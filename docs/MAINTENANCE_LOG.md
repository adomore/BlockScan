### 三处结构性改变

其余提交都是把数字拨回正确。只有这三项改变了「会不会再错」。

**1. 锁步铁律从比结构升级到比事实。** 原规则比对标题层级序列与代码围栏数，三对文档全部通过——而 README 对已经在事实层分叉：同一个 `cargo test` 围栏英文写 693、中文写 637；「审计引擎是分诊信号不是验证器」这句安全声明只存在于英文版；中文多记了四组 `monitor` 开关；事件表两边八行、第三列只有一边有。

结构与文字之间还有一层：**命令、条目数、表格列数、链接数不是措辞**，两种语言应当相同。`tests/docs_lockstep.rs` 用例 4 → 8。

四项断言里有一项被实测推翻后改掉了。原方案「围栏内非注释行逐字相同」在合法翻译上疯狂误报——示例输出里被翻译的中文表头、`<地址...>` 对 `<addr...>` 的占位符、当散文用的 JSON 字符串值。改为比对**命令 + 长 flag 面**（`blockscan`/`cargo` 调用归约成「程序 + 子命令 + 排序后的长 flag」），在两对维护良好的文档上零误报，同时在 README 对上揪出五条中文有、英文没有的示例命令。

刻意不比：段落数（中文断句更碎，按段落对齐会逼出机械直译）、链接目标（锚点本就是翻译）、围栏内数字（示例输出本就该不同）。

**2. 发布从手工改为打 tag 触发。** 手工打包正是校验和漂移的成因：归档在某人机器上产出、哈希被抄写、事后无从判断清单描述的是不是用户下载到的字节。现在清单由 job 从**它刚构建出来的**归档生成，并在同一个 job 里 `sha256sum -c` 自验。

注意 `ci.yml` 的触发是 `push: branches: [main]`，**tag push 不匹配**——所以 release job 是发布时唯一的闸门，它重跑 test 与 clippy，不假设 main 在打 tag 那一刻是绿的。它还会在构建前校验 tag 与 `Cargo.toml` 一致：不一致会产出「文件名写着一个版本、里面二进制报另一个版本」的归档，而这种错在上传之后才发现，代价是删 release。

**3. 校验和只剩一份。** 跟踪副本在归档存在之前无法写出，因此必然滞后一个版本；保留它就得靠自动化去追平，而不追平就又会漂。它还制造了一个自指：源码包是清单要列的条目之一，把清单塞进它所描述的归档里没有一致取值——写入哈希就改变了刚被哈希的 tarball。删掉之后，`.gitattributes` 里为它服务的 `export-ignore` 也一并移除，因为不动点已无法形成。

### 验证方式

- 每次提交前 `cargo test --all-targets --locked`（798 用例）。
- 事实层断言：**注入真实漂移**（删掉一条免责声明、去掉一个 `--throttle`），确认检查变红并指名缺失的 flag，还原后复绿。
- 偶发失败：单测连跑 20 次 + 6 轮完整集成测试（其中一轮故意与 `cargo clippy` 并行以重建资源竞争），26 次全绿，此前约每 6 次失败 1 次。
- clippy：**逐字复制 CI 的命令**（含 `-- -D warnings`），而非自制的近似命令。
- 发布产物：上传后**从 GitHub 下载回来**再校验，验的是用户实际会拿到的字节。
- README：过 GitHub 自家的 markdown API 渲染并中英并排比对。
- 二进制资产：本地哈希与 `raw.githubusercontent` 拉回的哈希比对，确认未被 `text=auto` 污染。

### 教训

审查中我自己犯了四次错，成因相同：**拿间接证据当结论**。

- 声称「clippy 无告警」，实际是没改过 `src/` 所以 clippy 复用缓存、一个字都没输出，而判定语句无条件跟在后面。
- 报告称某个数字「9 处出现三个互斥值」，实为 13 处，其中 6 处本就正确——检索式写窄了。
- 建议「在持有归档的机器上重新生成清单」，而那台机器很可能根本不存在：仓库当时 0 tag、0 release，归档大概率只是某次本地构建的残留。
- 本文与 [TASKS.md](TASKS.md) 最初把 T-08、T-11 写成没有内容的「未开始」，并把语料阻断只归给 T-09/T-10。原始清单说的是 `hard_blocked: [T-08, T-09, T-10]`、`held_by_policy: [T-11]`。已更正（`d69c880`）。

这与本次修的十几个文档缺陷同源——都是**抄了一份，而不是去看那个 job**。核门禁要逐字复制 CI 的命令，核状态要去查状态本身，而不是查引用它的文档。

第四次值得单独说，因为形态与前三次不同、也更难防：**一手材料就在磁盘上**（`blockscan-evolution/TASKS.yaml`），只是按 `.gitignore` 不入库，因而不在当时的视野里。于是我从一份**引用了它**的文件（`corpus/known_good.json` 的注释）反推，并把推断当作事实写了下来。

前三次的补救都是「换一个更权威的来源」；这一次没有别的来源可换。可换的是**表述**——拿不到权威出处时，应当写「据 X 推断」而不是直接断言，让后来的人一眼看出这条需要复核。`TASKS.md` 现在标了出处，就是这个意思。

同类现象在仓库里还有一个活样本：`tests/zz_corpus_measure.rs` 是产出 `AUDIT_DESIGN` 中「语料 172 发现 / 773 出现」这些数字的工具，却因 `/tests/zz_*.rs` 规则不入库，**那些测量因此无人能复现**——这正是 T-08 的问题陈述本身。
